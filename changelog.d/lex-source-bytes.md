- **A string literal's value is the bytes written in it, so bytes that are not UTF-8 reach the eval string as they are, where they became U+FFFD.** A source was decoded to text before lexing, and what was not UTF-8 was replaced. Upstream reads a file's bytes (`SourcePath::readFile` at 2.24.9) and its flex scanner lexes them (lexer.l), so a literal's value is its source bytes with escapes resolved, and the lexer here now reads bytes too. Upstream's string ends at a NUL in a double-quoted literal (`unescapeStr` stops at one), where nova-nix still keeps it. The lexer's token classes are upstream's, all ASCII: a letter outside ASCII, such as U+00E9, starts no identifier and continues none, so a name holding one is a syntax error, as it is upstream; a byte outside ASCII ends a path, a search path or a URI; and whitespace is space, tab, carriage return and newline, so a vertical tab, a form feed or a space outside ASCII such as U+00A0 is a syntax error. A comment may hold bytes that are not UTF-8. Columns still count characters where upstream's count bytes, a byte that continues a UTF-8 sequence taking its character's column, and a newline escaped in an indented string (`''\` before it) now ends a line for the positions after it. A string used as an attribute name (`{ "x" = 1; }`, `inherit "x";`) must be UTF-8, since attribute names are text here: one that is not is a syntax error at its string, where upstream makes a symbol of any bytes (the `attrpath` and `attrs` rules, parser.y). A key after a dot in an attribute path that fails to parse is reported at the key, where the error blamed the dot.
- **A source opening with a UTF-16 byte order mark is transcoded to UTF-8 before it is lexed, and malformed UTF-16 is a syntax error where it stands, where it was replaced.** An unpaired surrogate or an odd final byte has no UTF-8 spelling, and replacing it changed the source. Upstream reads no byte order mark (`EvalState::parseExprFromFile`, eval.cc at 2.24.9): no rule of its scanner but the catch-all takes a mark's first byte, and the grammar refuses the token that rule returns, so a file marked UTF-16 or UTF-8 fails to parse there. nova-nix reads both kinds of mark for the Windows tools that write them, and drops a UTF-8 mark as before.
- **Library API:** `Nix.Parser.parseNix` and `parseNixWithScope` take the source's bytes as read from its file and read any byte order mark themselves, and `Nix.Parser.readFileAutoEncoding` is removed: read the file with `Data.ByteString.readFile`. `Nix.Parser.Lexer.tokenize` takes bytes; `TokStringLit`, `TokStringEsc`, `StrLit` and `StrEsc` hold a `ByteString`; `EPathStr` holds its head piece as `Text` ahead of the parts after it; and `Nix.Parser.Internal.pMany` is removed, the attribute paths that used it now committing to the key after a dot.
