- **As root on Linux and macOS, a build runs as a member of `build-users-group`, `nixbld` by default, as upstream's does, so a builder can change neither the store nor another build, and no process it leaves outlives it.** A sandboxed build as root, which nova-nix refused for want of build users, now runs as one; it is refused only with `build-users-group` empty, under which an unsandboxed build runs as root. Each build takes the first member, in the group's order, whose lock file in upstream's user pool, `/nix/var/nix/userpool` or `$NIX_STATE_DIR/userpool`, is free, locked with `flock` as upstream's are, so a build of nova-nix's and one of an upstream daemon's on the same machine never share a user. While every member is taken the build waits, saying `waiting for a free build user ID for '<drv>'` once, and looks again every five seconds, upstream's default `poll-interval`. A group that is missing or has no members, a member that names no user, and a member that is the user nova-nix runs as fail the build in upstream's words. Every process of the member is killed before the build and once its builder ends, before any output is read. The store directory is made root's and the group's with mode 1775, as upstream's store open makes it; the directory the builder works in and the files nova-nix writes there are the member's; and a build is refused when the directory holding build directories, or one above it, is one every user may write, with upstream's `is world-writable or a symlink`. In the Linux sandbox the namespace's uid 1000 and gid 100 map to the member and the group, and the chroot's root and store directory are the group's, as upstream's are. Outside the sandbox, and in macOS's, the builder takes the member's uid, the group and, on Linux, the member's other groups, as upstream keeps them for a group such as `kvm`, set between the fork and the exec by a small C shim, since the process library can drop to another user only by looking it up in the forked child of a threaded process; the groups are looked up beforehand instead. A macOS build as a member is given upstream's temporary directory, `TMPDIR` or `/tmp`, in its profile, where a build as the invoking user keeps its own. An output whose root is not the member's is refused with upstream's `suspicious ownership or permission`, and one holding a node another user owns with `invalid ownership on file`, before it is made canonical; a passing output is made root's and read-only. A builtin builder still runs in nova-nix's own process, as root, where upstream runs it in the build's child as the member. The System V IPC objects upstream removes for a macOS build user are not removed, and `auto-allocate-uids` is not read.
- **Library API:** The new `Nix.Builder.BuildUser` decides whom builds run as (`buildUsersFor`, `defaultBuildUsersGroup`, `userPoolDir`), chooses a member over a capability record of the user database (`acquireBuildUser`, `UserDatabase`) and holds one for a build (`withBuildUser`), kills a member's processes (`killBuildUser`) and runs a builder as one (`runAsBuildUser`), and answers whether a daemon is to refuse a peer for its primary group (`peerInBuildUsersGroup`), which nothing calls yet. `BuildConfig` gains `bcBuildUsers`, so a record built without a default needs it; `defaultBuildConfig` builds as the user nova-nix runs as. `Nix.Config.NixConfig` gains `ncBuildUsersGroup`. `Nix.Store.Metadata.foreignOwnedNode` takes whom the output belongs to (`OutputOwner`), and `ownedByAnother` tests an output's root. In `Nix.Builder.Sandbox`, `PlanInputs` and `SandboxPlan` carry the ids the builder runs as (`BuilderIds`), `DarwinPlan` the build user, `darwinParameters` the build's temporary directory, and the chroot's store directory is a `SkeletonStoreDir`; the plan's format is version 5, which a helper of an earlier release refuses. `Nix.Builder.Sandbox` also exports `setupContext` and `errnoSuffix`, and `Nix.Builder.Sandbox.Spawn.withChroot` takes the build users' group.
