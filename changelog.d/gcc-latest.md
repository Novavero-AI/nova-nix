- **`pkgs/windows` builds `gcc-latest`, GCC 16.2.0 with C and C++ for `i686-w64-mingw32`, compiled by `gcc10` in the seed stdenv against MinGW-w64 v14.0.0, with GMP, MPFR and MPC built in its tree and libgcc and libstdc++ compiled by the compiler the same make links: the GCC nixpkgs' `minimal-bootstrap` builds after GCC 10.** It takes nixpkgs' release, 16.2.0, which needs a C++14 compiler to build, and nixpkgs' GMP 6.3.0, MPFR 4.2.2 and MPC 1.3.1, the releases GCC's own `contrib/download_prerequisites` fetches for an in-tree build of 16.2.0. nixpkgs builds this GCC in pieces, GMP, MPFR, MPC, libiberty, libbacktrace, the compiler, libgcc and libstdc++ each a derivation of its own, and joins them with a wrapper that points the compiler at musl, libgcc and libstdc++. Here, as in `gcc10`, the compiler is one build, a cross compiler given the current MinGW-w64's headers and runtime with `--with-headers` and `--with-libs`, which GCC copies into its own prefix and hands the compiler it links when it builds libgcc and libstdc++, so the driver finds the runtime and both libraries with no flag and no wrapper, and neither of nixpkgs' two patches, which serve its separate builds, applies. nixpkgs' choices carry over where they mean the same here: `-O1` for the compiler and `-O0` for libstdc++, `--disable-gcov`, `--enable-linker-build-id`, which has every link this compiler makes write a CodeView build ID, the deletion of the configure arguments from the top-level Makefile, which keeps the store paths they name out of `gcc -v`, and the removal after the install of the `install-tools` directories, libstdc++'s Python pretty-printers and the manual and info pages. The install removes libstdc++'s gdb script too, which loads those printers, and the `share` directories the removals leave empty. `--enable-default-pie` is left out: GCC compiles 32-bit Windows code without PIC whatever it is told, so the flag would only pass `-pie` to every link, for which binutils' `ld` writes an empty export table into a program that is relocatable without it. The build names binutils' `windres` by the target's name, as it names the compilers: GCC 16 built for Windows embeds a manifest that runs its driver and compilers with the UTF-8 code page, compiled by `windres`, which configure looks up under its bare name, and `PATH` has none. libgcc is `-O2`, for the reason `gcc10`'s is, and its debugging information is stripped after the install, as nixpkgs strips it. The thread model is win32, this target's default, under which libstdc++ has `std::thread` because MinGW-w64 v14.0.0's headers name Windows 10. As in `gcc10`, `--disable-win32-registry` is not nixpkgs', `--disable-shared` keeps libgcc and libstdc++ static, exceptions are SJLJ, and no program the rung installs carries the time it was built. CI builds the rung on x64 and ARM64 Windows in a stage of its own, GCC 16 (Windows), which starts from the store GCC 10 (Windows) hands it. Its `gcc` compiles and links a C23 program, its default, that uses `constexpr`, `typeof`, `nullptr`, `bool` and `_BitInt(128)`, and its `g++` a C++20 program, its default, that uses `std::format`, concepts, ranges, `std::span`, a three-way comparison and four `std::jthread` threads synchronized with a `std::mutex` and a `std::condition_variable`. Each program prints the compiler's version and default standard and the runtime's release, and each check compares what it prints and its exit status with what the C and C++ standards define, and pins the DLLs it imports, the libgcc, libsupc++ and libstdc++ functions it links, that it carries one build ID and that it has no debugging section. A third check reads the time stamp in the header of every program the rung installs and compares the list with one in which each is zero.
