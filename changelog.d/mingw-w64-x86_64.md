- **`pkgs/windows` builds `mingw-w64-crt-x86_64`, MinGW-w64 v14.0.0's runtime for `x86_64-w64-mingw32`, compiled by `gcc-core-x86_64` in the seed stdenv: the runtime the x86_64 GCC is given.** It is `mingw-w64-crt-latest`'s build for the other target, as nixpkgs' `mingw_w64` builds it for an x86_64 host: `--host=x86_64-w64-mingw32`, `--disable-lib32 --enable-lib64`, nixpkgs' flags for that host, and msvcrt.dll, the runtime the ladder links, compiled against `mingw-w64-headers-latest`, whose files serve either target. The 64-bit libraries install in `lib`, the directory the runtime's configure names for an x86_64 host. `gcc-core-x86_64` has no runtime yet, so configure's link to learn the suffix of executables fails, as the runtime's configure lets it, and its link with `-nostdlib`, which asks whether `ld` defines `__ImageBase`, is one that needs none. CI builds the rung in the x86_64 stage on x64 and ARM64 Windows. One check pins every file the runtime installs, each one Homebrew's mingw-w64 14.0.0 installs for x86_64 too, and the global symbols of `crt2.o`, which are those of the `crt2.o` in that package, so that the `__ImageBase` test, which changes the objects and not the build's exit status, shows if it fails on Windows. The other has `gcc-core-x86_64` link a program against the runtime, given its directories with `-B` and `-isystem` as GCC's build gives a compiler its target's runtime, that prints the release and msvcrt.dll version the headers name and calls `gettimeofday`, `_recalloc` and `_byteswap_ushort`, each linked from the runtime's libraries, and reads the program's PE header, which names an x86_64 PE32+ image.
