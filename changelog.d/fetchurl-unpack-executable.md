- **`builtin:fetchurl` restores the NAR it downloads when the derivation's `unpack` is true, and makes its output executable when `executable` is true, as upstream's does, so a `<nix/fetchurl.nix>` fetch with either attribute builds.** The bundled `<nix/fetchurl.nix>` declares a recursive hash for either, and nova-nix's builtin refused every recursive hash, so such a fetch evaluated and then failed to build. Upstream's builtin (`builtinFetchurl` in builtins/fetchurl.cc) restores the download as a NAR when `unpack` is `1`, decompressing it with xz first when the URL ends in `.xz` and never otherwise, writes it as the output file when `unpack` is anything else, and then sets the output's mode to `0755` when `executable` is `1`. nova-nix does the same, restoring through the streaming restore the substituter uses and decompressing through nova-cache's xz decoder, so neither the download nor the archive is held whole. Under `executable` it marks a regular file and leaves a directory as it is, since a NAR records no mode for a directory. A restored root that is a symlink fails that URL, and the next is tried, rather than being followed: upstream's `chmod` follows the link, but in the build's child process, after its `chroot` when the build is sandboxed and as the build user when there are build users (`LocalDerivationGoal::runChild` in local-derivation-goal.cc at 2.24.9, `UnixDerivationBuilderImpl::runChild` in unix-derivation-builder.cc at 2.36.0), where a file outside the build is absent or not the build user's to change, so the `chmod` fails the build there, while nova-nix runs a builtin as the invoking user and following the link would change the file it names. The output is held to the hash the derivation declares, in the mode it declares whatever made the output, as upstream's `registerOutputs` holds it: a flat hash needs a regular file its owner may not execute and is of its bytes, and a recursive one is of the output's NAR, the executable flag included. Registration then gives it the store's canonical metadata, so an executable file and every directory are `0555` and every other file `0444`, as upstream leaves them. A fetch of an `.xz` URL without `unpack` keeps the bytes it downloads, as upstream's does. As with a flat hash, each URL a derivation lists is held to the hash before the next is tried, so a mirror that serves the wrong tree is passed over. Three things differ from upstream. nova-nix restores only an archive in the canonical form upstream writes, failing one with bytes after its end or with a file's fields out of order, where upstream's restore stops reading at the archive's end and takes those fields in either order (`parse` in archive.cc at 2.24.9). An archive that fails to parse is retried as a torn transfer is, as the substituter retries one, where upstream fails the build at once. And the xz decoder's memory is bounded at nova-cache's default of 1 GiB, as the substituter's is, where upstream's libarchive decoder has no bound; the largest xz preset needs about 65 MiB.
- **Library API:** `Nix.Substituter` exports `narStreamFailure`, the retry class of a streamed NAR's failure, and `withXzAttempt`, which runs a consumer over an xz-decompressed chunk source and ends the attempt with the class of a decoder failure.
