- **`pkgs/windows` builds `gcc-core-x86_64`, GCC 16.2.0's C compiler and libgcc for `x86_64-w64-mingw32`, compiled by `gcc-latest` in the seed stdenv: the GCC core that compiles the x86_64 runtime.** It is MinGW-w64's build guide's GCC core and nixpkgs' `gccWithoutTargetLibc`, the compiler a cross toolchain builds before its target's C library exists, and the second rung of the ladder's x86_64 toolchain. Its sources and configuration are `gcc-latest`'s, GCC 16.2.0 with GMP, MPFR and MPC built in its tree, for the other target: the compiler runs on i686 Windows, writes x86_64 code through `binutils-x86_64`'s assembler and linker, and reads the current MinGW-w64's headers, the same files for either target. make builds and installs the compiler and libgcc alone, as the 4.6.4 `gcc-core` does, which is what compiling the runtime needs; libgcc is static and single-threaded, as nixpkgs has it for this compiler, and links nothing, so it needs only the headers. nixpkgs' flags carry over where they mean the same; those naming target libraries the build never configures, and three read by no configure of 16.2.0's tree, have nothing to do. The compiler and libgcc are `-O2`, configure's own optimization, without the `-g` nixpkgs strips after its install, libgcc's own `-g` is stripped here too, and no installed program carries the time it was built. CI builds the rung in the x86_64 stage on x64 and ARM64 Windows. One check has the compiler read `windows.h` and compile a function that divides two 128-bit integers, which `ld` links with libgcc and no runtime into a program that runs and exits with the quotient, and compares the target, version and thread model the driver reports, the object's symbols, and the machine and optional header magic read from the program's PE header with what the configuration and the formats define; the other compares the time stamps of the installed programs with a list in which each is zero.
