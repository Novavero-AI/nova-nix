- **A path value inside a store path is copied to the store under its base name when it is coerced, as every other path is, so a derivation in a nixpkgs imported from a store path gets upstream's drvPath and output path.** The path coerced to itself, with the enclosing store path as context, wherever it was interpolated, named in a derivation's `args` or environment, joined by `concatStringsSep` or written by `toJSON`. Upstream's `copyPathToStore` has no store case (eval.cc): it copies the path under `path.baseName()`, so `./build.kaem` in a nixpkgs fetched with `fetchTarball`, from a channel or as a flake input becomes `/nix/store/<hash>-build.kaem`, and a path that is exactly a store path is copied under its `<hash>-<name>` base name. Every derivation naming such a path therefore had a drvPath and output path of its own, nothing above it substituted from cache.nixos.org, its closure took in the whole enclosing tree, and its builder read its source inside that read-only tree: nixpkgs 26.05's `minimal-bootstrap.mescc-tools` now evaluates to `/nix/store/53zd871rgpcvi7qmqkffxhzaiq0is7k4-mescc-tools-1.9.1`, the path cache.nixos.org holds, where nova-nix gave another. drvPaths change for anyone whose nixpkgs lives in the store. The copy is read from the store nova-nix was given, so under `--store` and on Windows it is found where the store text names it, under the case-hack the store's volume keeps.
- **What a coerced store path now does follows from the copy, as upstream's does.** A read-only `eval` computes the copy's path without writing it, so `import "${/nix/store/<hash>-<name>}/default.nix"` fails with `path '/nix/store/<hash>-<hash>-<name>' is not valid` where it used to import, as upstream's read-only `realisePath` refuses it; `import /nix/store/<hash>-<name>`, which copies nothing, and `--read-write-mode` still import it. Under `--pure-eval` or `--restrict-eval` a path inside a store path that is not allowed is refused when it is coerced, as upstream's accessor refuses the read, where it used to coerce to itself unchecked.
- **A coerced path that is a symlink is copied as the link, with the links among its ancestors followed, inside a store path and outside it, as 2.34.9 and newer copy it; 2.24.9 copied what the link points to.** Upstream's `copyPathToStore` resolves a path's ancestors only from 2.34.9 (`SymlinkResolution::Ancestors`, eval.cc), where 2.24.9 resolved it in full (eval.cc), and nova-nix follows the newest release: `"${./link}"` gives the copy of the link where it gave the copy of its target. Under `--pure-eval` or `--restrict-eval` the link is read in place, so a link to a path outside the allowed ones is copied rather than refused, as upstream's accessor reads it. `builtins.path` and `builtins.filterSource` still copy what a link points to, as every release does (`addPath` in primops.cc), now inside a store path too, where they copied the link, and `builtins.storePath` of a path inside a store path that is a link names what it points to, as upstream resolves it in full (`prim_storePath` in primops.cc). Every link these follow is read in the store nova-nix was given once a path is in the store, a host link into it and an absolute link inside it included, as upstream resolves a path over the union of the host's file system and the store (`rootFS` in the `EvalState` constructor, eval.cc, from 2.34.9), so under `--store` elsewhere a path through a host link into the store reaches what it names there. The store directory and its ancestors are never taken for links for a path in the store, as upstream's store accessor looks for links only beneath the store directory (`PosixDirectorySourceAccessor::openParent` in posix-source-accessor.cc at 2.35.4 and 2.36.0), so with a `--store` directory that is a symlink store text stays in the store and `readFileType`, `filterSource` and a filtered `builtins.path` of a store path read it. On Windows a reparse point whose target no path value names, a volume mount point or a UNC link, is not walked and is left for the read to cross, as a POSIX read crosses a mount.
- **Library API:** `Nix.Store.CaseSensitive` exports `pathCaseHack`, the case-hack mode a read of path-value text runs under given the store volume's sensitivity. `Nix.Eval.Policy` exports the walk of a path through its symlinks, `walkPath`, pure over path-value text with the read of a link as an argument, and its rules: `PathRules` and `hostPathRules`, `SymlinkResolution`, `LinkTarget` and `linkTarget`, `WalkStop`, `storeRootPrefix` and `windowsLinkTargetJoins`.
