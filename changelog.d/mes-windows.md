- **`pkgs/windows` builds GNU Mes 0.27.1 on the Windows stage0 tools: `mes.srcPost` with mes-m2.exe, `mes.libs`, the Mes C library compiled by MesCC, `mes.compiler`, mes.exe compiled by MesCC, and `mes.libc`, the library's sources for TinyCC.** They are nixpkgs' `minimal-bootstrap/mes` derivations, each an `i686-windows` `kaem.runCommand` script on stage0-pe32's bin directories, built from the Novavero-AI/mes fork at d9ab4ea, which ports Mes 0.27.1 to Windows and carries nixpkgs' i686 C library fixes as commits. NYACC is nixpkgs' 1.09.1, fetched through a `mirror://savannah` site copied from nixpkgs' mirror list. Three things differ from nixpkgs. The paths Mes reads from the environment, `MES_PREFIX`, `GUILE_LOAD_PATH` and MesCC's `M1` and `HEX2`, stay there, set by every derivation that runs Mes and given to callers as `mes.env`, where nixpkgs writes them into Mes's C and Scheme source: the builder spells a store path `C:\nix\store/...`, and the backslash would start an escape in a string of either language. Mes's arena is 20,000,000 cells, set in the environment as well, since nixpkgs' 100,000,000 with its stack is more than the 1 GiB the Windows port reserves for all of Mes's memory; the cells Mes keeps across a collection have to fit in the tenth past the arena, and CI measures them while MesCC compiles libc+tcc, the largest library. And MesCC links a Windows program at `--base-address 0x400000`, the ImageBase of the port's PE header, starting it from a crt1 assembled from the port's M1 startup, which splits the command line Windows hands a program into argc and argv. `mes.libc` has no `include` link, which nixpkgs makes with a symlink the Windows library cannot. CI builds all of it on x64 and ARM64 Windows from the seed, runs mes-m2 and mes with `--version`, and runs a program MesCC compiled with mes, checking what it prints and the status it exits with.
