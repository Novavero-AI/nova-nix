- **`pkgs/windows` has the stdenv that replaces the MSYS2 one: `seedStdenv`, made only of tools built from stage0-pe32's seed, with busybox-w32's sh as the builder and its applets as the coreutils, sed, grep and awk, `gnumake` as make, and `tinycc-native`, on msvcrt.dll, as the C compiler and linker, so no MSYS2 or MinGW-w64 package is in the closure of anything it builds.** Its `mkDerivation` takes the stage-1 stdenv's attributes and runs the same phases from a `setup.sh` written for POSIX sh, and `pkgs/windows`' GNU Hello package builds with it unchanged. busybox-w32's applets are commands of their own through a launcher beside a copy of `busybox.exe`, as w64devkit installs them, since GNU make runs a recipe line with no shell syntax itself and `busybox --install`'s hard links would each be a copy in a NAR. Every path the stdenv passes on is respelled with forward slashes, since the builder spells the store `C:\nix\store` and a backslash is an escape in the sed scripts and C strings configure writes. A `config.site` gives configure the two things it cannot detect: `PATH_SEPARATOR=';'`, since busybox's sh runs its own `sh` applet whatever `PATH` holds, and `ac_executable_extensions=.exe`, since busybox's `test -x` does not add the suffix. configure is told `--build=i686-pc-mingw32`, since `config.guess` cannot read busybox's `uname`; `LD` is tcc, as nixpkgs' minimal-bootstrap sets it, since the iconv and gettext checks fail with no `ld`; and `BB_OVERRIDE_APPLETS=make` keeps busybox's own make from shadowing GNU make. TinyCC's headers gain MinGW-w64's `sdkddkver.h`, without which gnulib calls Vista's `GetFinalPathNameByHandle`, which they do not declare. The stage-1 stdenv's fixup phase, which copies each DLL an output imports from a build input beside it, is left out, since nothing built from the seed reads a PE import table. The MSYS2 stage-1 stdenv and its seeds are transitional: they stay the package set's `stdenv`, which CI's E2E, publish and public-cache jobs build Hello with, until the seed ladder builds every package they build, which needs GCC on the ladder for C++, x86_64 output where the ladder writes i686, MinGW-w64's headers and runtime, and binutils' objdump for that DLL bundling, and are then deleted. CI builds Hello with the seed stdenv on x64 and ARM64 Windows and runs it, and a test reads its closure: the leaves are the seed and the ladder's source archives and files, and neither stage-1 seed is in it, where both are in the closure of Hello built with the stage-1 stdenv.
