- **`push` uploads a NAR larger than 64 MiB in parts of 64 MiB through nova-cache's multipart upload, so a cache behind a proxy that refuses a large request body takes it.** Each NAR went in one `PUT /nar/<file>`, and Cloudflare in front of cache.novavero.ai refuses a body over 100 MB with 413, so once GCC 16.2.0's source (107,200,936 bytes) joined the ladder, every publish from main failed at that path. Upstream's `HttpBinaryCacheStore` also sends each file in one PUT (`upsertFile` in http-binary-cache-store.cc:130-142 at 2.24.9), so the parts follow nova-cache's protocol: `POST /nar/<file>/uploads` begins an upload, `PUT /nar/<file>/uploads/<id>/<n>` sends each part in order, and `POST /nar/<file>/uploads/<id>` completes it with the part count and the total size. A NAR of 64 MiB or less still goes in one PUT, and so does a larger one when the cache answers the beginning with 404, as a nova-cache without the multipart upload does, so a push to such a cache works as before. A part, or the request that begins an upload, that fails as upstream's transfer layer retries a transfer, its response lost or an error status such as 503, is sent again with upstream's attempts and backoff, which it applies to an upload as to a download (filetransfer.cc:421-509): the server replaces a part it holds, so a part that did arrive is not doubled. A part answered 404 or 409 means the server no longer holds the parts before it, and a new upload begins. A completion answered with anything but 200, or not at all, may still have joined the NAR, so the push goes on and the narinfo decides: the server checks its FileSize and FileHash against the stored NAR, and a narinfo it refuses then uploads the NAR again. The narinfo is sent in the second phase with the others, so a path is still never announced before its references. A push begins at most three uploads of one NAR, then fails naming the request and the server's answer. A push request that gets no response is reported with the client's failure alone, where it printed the client's whole request record, and a refused `narinfo-hashes` request carries the server's message. The compressed NAR is still held in memory whole, as for one PUT: nova-cache's zstd encoder is one-shot, and an upload is begun under the object's name, which for zstd is the hash of the whole compressed file.
- **Library API:** `Nix.Push.PushConfig` gains `pcPartSize`, a `PartSize` (from `mkPartSize`, or `defaultPartSize` for 64 MiB), and `pcRetry`, a `Nix.Http.FetchRetryPolicy` (`defaultFetchRetryPolicy` for upstream's); a caller that builds a `PushConfig` sets both. `splitParts` cuts a NAR into the parts of an upload. `Nix.Http.exceptionFailure` classifies a client failure as `fetchExceptionFailure` does, with the caller's message.
