- **On Linux a build runs in a sandbox by default, as upstream's does: in fresh user, mount, PID, IPC and UTS namespaces, with a chroot that holds the closure of its inputs, and in a network namespace of its own, holding only a loopback interface, unless the derivation is fixed-output.** Upstream sandboxes every build on Linux unless `sandbox` says otherwise (`Settings::sandboxMode` in globals.hh at 2.24.9, `LocalSettings::sandboxMode` in local-settings.hh at 2.36.0), and nova-nix ran every builder with the whole filesystem and the network in reach. A build an evaluation starts for an import from a derivation runs in the sandbox too, whichever command evaluates. The new `nova-nix-sandbox` helper, a C program installed beside `nova-nix`, makes the namespaces and the chroot and executes the builder, following upstream's `startBuilder` and `runChild` (local-derivation-goal.cc at 2.24.9): the setup runs between the namespaces' creation and the builder's exec, where nova-nix can run nothing, since the process library gives no hook between fork and exec and a child forked from the threaded GHC runtime may make only async-signal-safe calls. The helper is spawned with an empty environment, so its dynamic loader reads no variable a derivation sets, such as `LD_PRELOAD`; the builder's environment travels in the helper's plan and is applied only at the builder's `execve`, as upstream's is (`LocalDerivationGoal::runChild` in local-derivation-goal.cc at 2.24.9, `UnixDerivationBuilderImpl::runChild` and `execBuilder` in unix-derivation-builder.cc at 2.36.0). A build sees what upstream's sandboxed build sees: uid 1000 and gid 100, mapped to the invoking user, upstream's `/etc/passwd` and `/etc/group`, the host name `localhost`, itself as PID 1, a fresh `/proc`, a tmpfs `/dev/shm`, upstream's `/dev` nodes, a writable `/tmp`, its build directory at `sandbox-build-dir`, `/build`, which `NIX_BUILD_TOP`, `TMPDIR`, `TEMPDIR`, `TMP` and `TEMP` name, and upstream's `HOME`, `/homeless-shelter`. The directory bound there is one inside the build's own, as upstream binds `topTmpDir + "/build"` (`LocalDerivationGoal::startBuilder` in local-derivation-goal.cc at 2.24.9, `ChrootDerivationBuilder::setBuildTmpDir` at 2.36.0), so a builder that opens what it sees to everyone leaves the 0700 directory around it closed to every other user. Its environment still differs from upstream's where an unsandboxed build's does: `PATH` holds the builder's own directory where upstream's is `/path-not-set`, `PWD`, `TERM` and `NIX_OUTPUT_CHECKED` are not set, the builder's `argv[0]` is its whole path where upstream's is its name, and its output reaches the log through a pipe where upstream's goes through a pseudo-terminal. An output that is already valid, or that a check builds again, is still written at a scratch path whose hash is rewritten in it afterwards, as outside the sandbox, where upstream's sandboxed build writes it at its own path, which the chroot leaves free (`LocalDerivationGoal::needsHashRewrite` and `LocalDerivationGoal::startBuilder` in local-derivation-goal.cc at 2.24.9, `ChrootDerivationBuilder::needsHashRewrite` at 2.36.0). A fixed-output build gets the host's network, its `/etc/resolv.conf`, `/etc/services` and `/etc/hosts`, and the `ssl-cert-file` bundle at `/etc/ssl/certs/ca-certificates.crt`; any other gets `/etc/hosts` naming the loopback. Every host path is bound read-only, the build directory alone writable, where upstream binds them plainly: without a daemon the builder runs as the invoking user, so a writable bind would let a build change a valid store path, the bundled shell later builds run, an `--exec-wrapper` launcher, or a file of the user's a `sandbox-paths` entry names. The one exception is upstream's too: where the kernel will not mount a devpts of the sandbox's own, the host's `/dev/pts` and `/dev/ptmx` are bound writable instead (`LocalDerivationGoal::runChild` in local-derivation-goal.cc at 2.24.9, `ChrootLinuxDerivationBuilder::enterChroot` at 2.36.0). A `sandbox-paths` target, or `sandbox-build-dir`, that is not absolute or has a `..` component is refused, since joined to the chroot it names a path outside it, and so is one whose path crosses a link in the chroot, such as `/dev/fd` or a link an earlier entry copied in; upstream joins a target to its chroot as it is and follows what it finds. Each directory on the way is opened by its descriptor, which takes search on it and not read, and a bind is made read-only through the descriptor of the mount just made, not by its path. Once the builder has ended, before anything reads an output, the chroot is closed to every other user: the directories from its root down to its store directory become 0700, and every directory in the store directory's subtree, an output's own included, becomes 0700, each read without following a link and changed only once its parent is closed, since a fixed-output builder, which keeps the host's network, could have passed another user a descriptor for one of them. Whether the builder left an output writable by others is read first, so such an output is still refused. A process of the same user, a concurrent build among them, is not kept out. A bind is read-only through every mount beneath its source, which a recursive bind brings along, on any kernel: in one step through `mount_setattr` from Linux 5.12, and before it by remounting each mount `/proc/self/mountinfo` lists there. The builder gains no privileges through its exec, from a setuid program or file capabilities a `sandbox-paths` entry makes reachable, as upstream's builder gains none by default (`allow-new-privileges`, globals.hh at 2.24.9, local-settings.hh at 2.36.0), and it starts with an empty session keyring of its own, so it does not inherit possession of the invoking user's session keyring. That is all the keyring stops: the builder runs as the invoking user's uid, so `/proc/keys` shows it the user's keys, and that uid may link the user keyring into the builder's own, so a builder that tries can read the keys the user keyring holds. Only a filter refusing `keyctl`, `add_key` and `request_key` closes that, as it would for upstream's single-user builds; upstream's builder runs as a build user, with no keys of the invoking user's. An interrupt, or nova-nix's end, makes the helper kill the builder, whose PID namespace the kernel ends with it, and a helper killed outright takes the builder with it unless the builder has cleared its own parent-death signal, which upstream's builder, PID 1 of its namespace too, can as well; nova-nix returns from an interrupt only once the helper has reaped the builder, so no process a builder started outlives the build, and the chroot is removed after them. The helper puts `SIGCHLD` back to its default before it starts a builder, as upstream's `initNix` does (shared.cc), so a nova-nix started with `SIGCHLD` ignored still sees its builder end. The settings are upstream's, under its names, aliases and defaults: `sandbox` (`build-use-chroot`, `build-use-sandbox`) takes `true`, `relaxed` or `false`, and refuses anything else with `option 'sandbox' has invalid value`; `sandbox-paths` (`build-chroot-dirs`, `build-sandbox-paths`, and `extra-` for each) binds `TARGET=SOURCE` entries, with `?` after a source that may be missing and a store source's closure bound beside it; `sandbox-fallback`, `sandbox-build-dir`, `sandbox-dev-shm-size`, `require-drop-supplementary-groups` and `ssl-cert-file` are read too. `build`, `eval` and `trust`, each of which evaluates, take `--sandbox`, `--no-sandbox` and `--relaxed-sandbox`, and upstream's `--build-use-chroot` and `--build-use-sandbox`, which mean `--relaxed-sandbox` as upstream's do: it registers the setting's older names on all three flags, and the last registration holds them (`Args::addFlag` in args.cc). Under `sandbox = true` a derivation setting `__noChroot` fails with upstream's error; under `relaxed` it, and a fixed-output derivation, builds unsandboxed. A setup step that fails is reported with the words of upstream's error for it and the system's text for the errno, after `while setting up the build environment: ` on the same line, where upstream prints that context as a trace line and the error after an `error:` of its own. A derivation whose builder is a host program, such as `/bin/sh`, now needs `--no-sandbox` or a `sandbox-paths` entry binding it: a release archive for Linux carries a static busybox in `libexec/nova-nix/sh`, which `sandbox-paths` names as `/bin/sh` unless an assignment replaces it, as packaged upstream Nix carries its sandbox shell, and a `cabal install` keeps upstream's empty default. BusyBox is GPL-2.0, so each release also carries, beside the archives, the source that busybox was built from, Ubuntu's source package for that version, which the copyright notice beside the binary names. Ubuntu since 24.04 lets an unprivileged process make a user namespace but denies it capabilities there unless an AppArmor profile with a `userns` rule covers the program, so there a build runs unsandboxed unless such a profile names `nova-nix-sandbox`; upstream's root daemon is not restricted that way. A system that cannot make the sandbox builds without it under `sandbox-fallback`, as upstream does, but prints one warning naming the cause, where upstream prints nothing, since nova-nix without a daemon falls back on every stock Ubuntu; with `sandbox-fallback = false` the build fails with upstream's `this system does not support the kernel namespaces that are required for sandboxing`. As root, a sandboxed build is refused before anything is set up, whatever `sandbox-fallback` says: upstream builds as root under build users, uids of their own, which nova-nix does not have yet, and without them the builder would map to root on the host; `--no-sandbox` builds it unsandboxed. Windows builds are not sandboxed, and `sandbox = true` there falls back the same way.
- **Library API:** `Nix.Builder.BuildConfig` gains `bcSandbox`, a `SandboxConfig` from the new `Nix.Builder.Sandbox`, which also holds the settings' types, the decision (`sandboxUse`, `buildNetwork`), the helper's plan (`sandboxPlan`, `renderPlan`), the chroot (`chrootSkeleton`) and the helper's reports (`parseStatus`, `helperOutcome`); `defaultBuildConfig` leaves the sandbox off (`defaultSandboxConfig`), since finding the helper takes IO. The new `Nix.Builder.Sandbox.Spawn` probes the system (`sandboxAvailability`), runs the helper (`runHelper`) and makes the chroot (`withChroot`). `Nix.Config.NixConfig` gains `ncSandbox`, `ncSandboxFallback`, `ncSandboxPaths` (a `PathSetValue`), `ncSandboxBuildDir`, `ncSandboxDevShmSize`, `ncRequireDropSupplementaryGroups` and `ncSslCertFile`, so a record built without a default needs them. `Nix.Realise` exports `derivationBoolAttr`, upstream's `getBoolAttr`. `Nix.Builder.BuildLayout` also holds the `HOME` a builder is told of (`layoutHome`). The library's `directory` floor rises to 1.3.9, the first whose `removePathForcibly` works relative to each directory's descriptor and never follows a link, which removing a chroot relies on.
