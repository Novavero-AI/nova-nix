- **A program's names are interned in the order upstream's parser interns them, so a set holds its attributes in upstream's order and `let za = 1; in ({ }: za) { zb = 1; za = 2; }` names `za` as the unexpected argument, as upstream does, where it named `zb`.** Both evaluators hold a set's attributes sorted by symbol (`Bindings`, attr-set.hh at 2.24.9), and a symbol's place is the order its name was interned in, so that order decides which of two failures wins wherever a walk over a set stops at the first: the unexpected argument a call names is the first in symbol order (eval.cc:1566-1576). Upstream's parser interns each name in the action of the rule that reads it (parser.y:179-483), and bison runs a rule's action once the rule's right-hand side is parsed, the deferred actions of its GLR stacks included: a variable where it is read, an attribute path's names before the value bound to it, a `let`'s bindings before its body, a set of formals before the function's body and each formal after its default, an attribute path before its `or` default, and a plain `x:` argument and an `@` name after the function's body. nova-nix interned names as its compiler met them: a `let`'s body before its bindings, a function's body before its formals, an `or` default before its path, a variable bound in scope only where it is bound, and an attribute path written in several places as one set. The parser now notes each name where upstream's interns one, and the evaluator interns them in that order before it compiles. A key `${"name"}`, which upstream's parser makes static, has its name interned in place though it stays dynamic here; one whose expression is an indented string of a single literal piece or a URI, which upstream makes static as well, is still interned when it compiles or evaluates. The order still differs for a name either evaluator interns at startup, and for a name already in the table as something upstream keeps out of it: a string value, a path or search-path literal, or a source file's path, which nova-nix interns in the same table, though a literal now follows every name of its own file. - **Library API:** `Nix.Parser.parseNix`, `parseNixWithScope` and `parseNixFile` return a `ParsedSource`, whose expression `parsedExpr` reads and whose names, in upstream's interning order, `parsedNames` reads. `Nix.Eval.evalParsed` evaluates one, interning its names first, and `Nix.Eval.Compile.compileParsed` compiles one; `eval` on its expression interns the names in the order the compiler meets them. `Nix.Parser.Internal.ParseState` gains `psNames`, the names noted so far, latest first, which a state built outside the parser starts as `[]`, and `recordName` notes one.
