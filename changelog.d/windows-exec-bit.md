- **A program a Windows build marks executable with `chmod` is executable in its NAR, as on Linux, and the bin directories of `pkgs/windows`' stage0 tools mark theirs.** nova-nix keeps a regular file's executable bit on Windows as an NTFS alternate data stream, `<file>:nova.exec`, and only `builtin:unpack`, NAR restores, store copies and `builtins.fetchGit` ever wrote one, so nothing a builder made was executable: a program built on Windows had a NAR hash different from the same output's built elsewhere, and a substituted copy was not executable. `pkgs/windows` now pins stage0-pe32 at ed943c2, with its M2libc fork at 13e57eb, whose Windows `chmod` creates the stream when the owner execute bit is set and removes it when that bit is clear, the bit upstream's NAR serialisation reads (`S_IXUSR`), so a builder marks a program as it would on POSIX, and hex2's own `chmod(output, 0750)` marks what it links. The same M2libc's Windows `malloc` hands out 8-byte aligned memory, as Windows' own does on x86: it gave each block whatever alignment the end of the program's data left it, and Windows fails a file call whose name's buffer is at an odd address, so `chmod` failed silently in any program whose data ended at an odd byte, mescc-tools-extra's `chmod` among them. `stage0-pe32.kaem`, `mescc-tools` and `mescc-tools-extra` follow each `cp` with `chmod 555`, as nixpkgs' do. The single-file links stay unmarked, since nothing that writes them calls chmod: hex0 and hex1 are written by the seed and by hex0, which has to stay byte-identical to it, and the rest are linked by the hand-written hex2. hex2-new and kaem change with the fix; hex0 through M1 do not. CI checks on x64 and ARM64 Windows that every program in the bin directories carries the stream, and builds a fixed-output script whose declared hash is its tree's NAR hash on POSIX, with the file `chmod 555` marked executable and the one `chmod 755` and then `chmod 644` left plain.
