- **`pkgs/windows` builds `binutils-native-x86_64` and `gcc-native-x86_64`, binutils 2.46 and GCC 16.2.0 with C and C++ that run on x86_64 Windows and write `x86_64-w64-mingw32`, compiled by `gcc-x86_64` in the seed stdenv: the ladder's first tools that run as `gcc`, `g++`, `as` and `ld`, as the stage-1 stdenv's MSYS2 toolchain does.** Every rung before them runs on i686, and the x86_64 cross toolchain is named for its target. Each is a Canadian cross, as nixpkgs builds a toolchain whose host is its target: the stdenv's i686 triple is the build and `x86_64-w64-mingw32` the host and the target, so the programs take no prefix, the host's programs and GCC's target libraries are compiled by `gcc-x86_64`, a cross compiler of the same release as nixpkgs requires, and the programs the build runs itself by `gcc-latest`. The binutils flags are `binutils-x86_64`'s, and the GCC flags `gcc-x86_64`'s, but for what a compiler whose host is its target needs: GCC refuses `--with-headers` and `--with-libs` for it, so the build reads MinGW-w64's headers through `--with-build-sysroot` and `--with-native-system-header-dir`, as nixpkgs does, which also lets GCC's `limits.h` include MinGW-w64's, and the install copies the headers and the x86_64 runtime into the compiler's tool directory, where the installed driver finds them with no flag; `--with-as` and `--with-ld` name the native binutils. As nixpkgs' compilers do, it leaves `/usr/local/include` out of its search for headers, which a GCC whose host is its target otherwise searches ahead of the target's own, so a directory of that name on the build's drive cannot shadow MinGW-w64's. The thread model is win32 and libgcc and libstdc++ are static. MSYS2's GCC has the posix model and shared runtime DLLs that import winpthreads, which the stage-1 stdenv carries by putting its toolchain on `PATH` and copying DLLs beside each output, but its packages use neither: they are C, and GNU Hello built with it imports no DLL of GCC's or winpthreads. nixpkgs gives a thread model only to a GCC whose host is not its target, so its native MinGW-w64 GCC takes win32, the target's default, which needs no thread library the ladder does not build and under which libstdc++ has `std::thread`; static libraries leave a program importing no DLL of GCC's, which the seed stdenv, having no fixup phase, could not carry. CI builds both rungs on x64 and ARM64 Windows in a new stage, Native x86_64, which starts from the store GCC 16 x86_64 now hands on. One check has the tools assemble, archive and link an x86_64 program and an i386 one that run; two have `gcc` and `g++` link the C23 and C++20 programs `gcc-x86_64`'s checks link, threads and SEH exceptions included, and compare their output, imports and symbols with what the standards and the ABI define. Each also reads the PE headers of the rung's own `as.exe` and `ld.exe`, or `gcc.exe`, `g++.exe`, `cc1.exe` and `cc1plus.exe`, which are x86_64 PE32+ images, and finds that none imports a DLL of GCC's runtime, winpthreads or mcfgthreads; and a check per rung reads the time stamp in the header of every program it installs and compares the list with one in which each is zero.
