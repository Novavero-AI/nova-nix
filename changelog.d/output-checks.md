- **A build's output that its group or anyone else may write is refused, every output is made canonical before it is read or changed, and a fixed output is replaced by a fresh copy of itself before it is hashed, as upstream's are.** Upstream refuses such an output with `suspicious ownership or permission on '...' for output '...'; rejecting this build output`, since someone other than the build may have changed it, then makes the output canonical, so nothing in it is setuid, or open to another user's write or swapped link, while it is rewritten and scanned (`registerOutputs`, local-derivation-goal.cc at 2.24.9, derivation-builder-impl.cc at 2.36.0). nova-nix made an output canonical only once it was placed. A fixed output's fresh copy leaves behind the inode the builder wrote, so a descriptor the builder passed out of its build cannot change what is registered (the fresh copy in `registerOutputs`); the copy is made canonical in its turn, and it is the copy that is scanned and hashed, before it leaves the chroot. A fixed output that references a store path, itself included, is refused with upstream's `illegal path references in fixed-output derivation '...'` (the fixed-output reference check in `registerOutputs`), which nova-nix let through; upstream registers such an output under the path its references give it before it fails the build, and nova-nix registers nothing, as for a hash mismatch. On Linux an output's extended attributes, ACLs among them, are removed as it is made canonical, as upstream removes them (`canonicalisePathMetaData_` in posix-fs-canonicalise.cc), but for the three upstream's `ignored-acls` keeps by default, `security.selinux`, `system.nfs4_acl` and `security.csm`. A directory in an output that its owner may not search is given search before it is read, so it ends at 0555 where upstream's canonicalisation gives it 0444 and a single-user upstream build, not run as root, then fails to read beneath it. A sandboxed build's outputs go through all of it in the chroot and move into the store only when registered (the final move in `registerOutputs`), so a check's outputs, and the copy of an output that was already valid, never enter the store. A hash rewrite of an output's file opens it without following a link, and refuses one swapped in. An output holding a node another user owns is refused with upstream's `invalid ownership on file '...'` (`canonicalisePathMetaData_` in posix-fs-canonicalise.cc at 2.24.9) before it is made canonical, which would change that node, a hard link into the output among them. A directory output moves into the store by a rename, given owner write for it as upstream's `movePath` gives it (local-derivation-goal.cc at 2.24.9, unix/file-system.cc at 2.36.0), so it keeps its inodes and hard links, and a rename that fails fails the build, except across volumes, where the move copies. An output that is a symlink is there whatever it names, as upstream reads it with `lstat` (`registerOutputs`), where nova-nix took one naming nothing, or a sibling output not yet in the store, for a missing output. nova-nix now runs with upstream's file-creation mask, 0022, as every upstream command does (`initNix`, shared.cc): everything it creates is made under it, the store and its database, push and fetch caches, garbage-collector roots and out-links among them, and so is everything a builder it starts creates, so no ordinary build's output is refused.
- **Library API:** `Nix.Store` exports `useStoreFileMask`, which a program building through the library calls to give its builders upstream's mask, `replaceWithCopy` and `freshCopyPath`, and, for testing, `rewriteRegularFile`; `Nix.Store.Metadata` exports `writableByOthers` and `foreignOwnedNode`; and `Nix.Builder.BuildDir` exports `sandboxedBuildDir`, where a sandboxed build's own directory is. `Nix.Store`'s `placeInStore` and `addToStore` move a path by a rename that fails, rather than copies, except across volumes.
