- **The builtins that read a plain string refuse one with string context, as upstream's do: the regex of `match` and `split`, `getEnv`, the name of `toFile`, the algorithm of `hashString` and `hashFile`, `fromJSON`, `placeholder`, `parseDrvName`, `splitVersion`, both arguments of `compareVersions`, and the name `findFile` looks up.** Each read the string's text and dropped its context, so `builtins.toFile (builtins.appendContext "a" { ... }) "x"` wrote a file and `builtins.match` of such a regex matched. Upstream reads each with `forceStringNoCtx` (`prim_getEnv`, `prim_placeholder`, `prim_findFile`, `prim_hashFile`, `prim_fromJSON`, `prim_toFile`, `prim_hashString`, `prim_match`, `prim_split`, `prim_parseDrvName`, `prim_compareVersions` and `prim_splitVersion` in primops.cc), which refuses one with context as `the string 'a' is not allowed to refer to a store path (such as '...')`, naming the context's first element (eval.cc), and now so does nova-nix, with the reader that computed attribute names already use. A value that is not a string is refused in those positions with that function's `expected a string but found ...`, where each builtin had a message of its own. `findFile` reads the name after its search path entries, as upstream's does, so a failing entry is reported ahead of the name, and `match` and `split` compile the regex before they look at the subject, as upstream's do, so an invalid regex is reported ahead of a subject that is not a string.
