- **`pkgs/windows` builds MinGW-w64's headers and GCC 4.6.4's C compiler and libgcc for `i686-w64-mingw32` with the seed stdenv, the compiler compiled by `tinycc-native` and libgcc by that compiler: the driver, `cc1`, `cpp`, `collect2`, GCC's own headers and libgcc, with the binutils rung's assembler and linker.** It follows nixpkgs' `minimal-bootstrap/gcc/4.6.nix`, which builds the same release with tinycc, and builds what MinGW-w64's own build guide builds from one GCC build directory, with `make all-gcc` and `make all-target-libgcc`. The guide builds libgcc once MinGW-w64's runtime is installed, since its shared libgcc links against the runtime; libgcc here is static, as nixpkgs' is, links nothing and needs only the headers, so it is built in the same make, and the runtime, which this compiler compiles, is the next rung. libgcc is compiled without debugging information, which would name the build directory and the store paths the compiler read: `CFLAGS_FOR_TARGET=-O2` replaces the `-g` GCC's top-level configure adds to the target libraries' flags, and `LIBGCC2_DEBUG_CFLAGS=-g0` the `-g` GCC's Makefile adds to every libgcc compile. Its thread model is win32, on the Windows API alone, and its exceptions SJLJ, a 32-bit MinGW target's defaults. make runs `$NIX_BUILD_CORES` jobs, as `minimal-bootstrap/gcc/4.6.nix`'s does. `mingw-w64-headers` installs release v8.0.3, the newest whose runtime calls none of three builtins GCC 4.6.4 lacks, from the project's signed release archive. GCC is given them with `--with-headers`, which copies them into its own output as `i686-w64-mingw32/sys-include`, the directory a cross GCC searches for its target's headers, and its `limits.h` goes on to MinGW-w64's from there. GCC's manual prefers `--with-sysroot`, but GCC's top level hands each option to the configure of every library it builds, and mpc's libtool takes a sysroot for absolute only if it begins with `/`, which a store path on Windows does not; `--with-headers` is read by the top level and by `gcc` alone. The stdenv's `i686-pc-mingw32` stays the build and the host, so GCC is configured as the cross compiler it is: tcc compiles it against TinyCC's headers and msvcrt.dll, and its target has MinGW-w64's. Its programs install as `bin/i686-w64-mingw32-<name>.exe`, and `--with-as` and `--with-ld` compile in the paths of binutils' assembler and linker, which a cross GCC otherwise looks for in its own prefix. gmp, mpfr and mpc are built in the tree, as in nixpkgs. The edit of binutils' `fix-tinycc-attribute.patch` is made to GCC's copy of `include/ansidecl.h`: without it 25 calls in libiberty's `pex-win32.c` and `lrealpath.c` and in `gcc/config/i386/host-mingw32.c` reach the Windows API as cdecl, and pop arguments the function has already popped, on every program the driver starts. Three more settings are for TinyCC. `CFLAGS=-Dalloca=alloca`, since libiberty, gmp and mpfr each declare `alloca` in a way tcc rejects unless it is a macro. `LDFLAGS=-luser32`, since libiberty calls `CharLowerBuff`, and tcc links msvcrt and kernel32 alone where GCC's own MinGW links user32 into every program. And a new package, `mingw-w64-dirent`, MinGW-w64's own `dirent.c` compiled by tcc beside the `dirent.h` it is written for: libcpp reads a directory of precompiled headers with `opendir`, msvcrt.dll has none, and TinyCC's `dirent.h` declares an older `struct dirent`, against which that file compiles without a warning and then copies each name through a pointer nothing sets. The seed stdenv gains what the rung needs of it: `preConfigure`, nixpkgs' hook, which moves `mingw-w64-headers` to the directory its configure is in and unpacks GCC's three libraries where its configure looks for them; `configureScript`, nixpkgs' too, with which GCC configures from a build directory beside its source, as its installation guide recommends, since in the source GCC names the build machine's `fixincl` by two paths that differ and, with the program called `fixincl.exe`, make links `fixincl.o` alone; `configureFlags` joins the variables whose store paths are respelled with forward slashes, since GCC's configure writes the headers' and the two tools' paths into Makefiles and C strings; `config.site` answers that `atoll` exists, since TinyCC's `stdlib.h` defines it inline and `msvcrt.dll` exports none, so a link test finds none and GCC's `read-rtl.c` then defines a second; and `PATH_SEPARATOR` and `ac_executable_extensions` move from `config.site` to the environment, since GCC's top level runs the configure of each directory it builds for the build machine, and of each target library, with `CONFIG_SITE=no-such-file`, and in a native build that machine is this one. `tinycc-native`'s runtime gains an empty `libm.a`, as MinGW-w64's runtime has one: TinyCC finds a library only by a file, `msvcrt.dll` holds the math functions, and GCC links its `genautomata` with `-lm`; CI links a program with `-lm` and runs its `sqrt`. `fetchurl` takes nixpkgs' `mirror://sourceforge`. CI builds the three packages on x64 and ARM64 Windows, checks the driver's version line, and has the compiler compile a source to assembly, read `windows.h`, and compile a function that `ld` links and that runs. The assembly is compared with what GCC 4.6.4 built by another compiler writes for the same source, which holds constants `cc1` folds in its 64-bit arithmetic, in its floating point and through MPFR, so a `cc1` that tcc compiled wrongly shows.
