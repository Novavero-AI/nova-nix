- **A builder's environment holds `NIX_BUILD_CORES`, from the nix.conf setting `cores`, so nixpkgs' `setup.sh` runs `make` for a package with `enableParallelBuilding` with as many jobs as it does under upstream.** nova-nix set no such variable, and setup.sh reads an unset one as 1, so every such package built on one core. Upstream sets it in every builder's environment from `settings.buildCores` (`LocalDerivationGoal::initEnv`, local-derivation-goal.cc:1157 at 2.24.9) before it copies in the derivation's environment, so where a derivation's attributes reach the environment, which they do not under `__structuredAttrs`, an attribute of that name wins, as it does here. The setting is read as upstream's `cores` is (globals.hh:162): an unsigned integer under the grammar `max-call-depth` takes, also set through its alias `build-cores`; `0` is passed through, which setup.sh takes to mean every core `nproc` counts; a value that does not parse is refused as `setting 'cores' has invalid value '...'`, naming `cores` when it was set through `build-cores`, as upstream's error does; and `extra-cores` is an unknown name. A value past an unsigned 32-bit integer is refused, where upstream multiplies a unit suffix in 64 bits and keeps the low 32 (util.hh:126-143), so that its `cores = 4G` is 0, every core. With nothing setting it, the value is upstream's default (`Settings::getDefaultCores`, globals.cc:172). On Linux that is the CPU limit of the process's cgroup when it has one, found as upstream's `getMaxCPU` finds it (current-process.cc:28): the first `cgroup2` mount in `/proc/mounts`, read as glibc's `getmntent` reads it, joined to the group `/proc/self/cgroup` lists under no name, which is parsed as upstream's `getCgroups` parses it (linux/cgroup.cc), and that group's `cpu.max` quota over its period, rounded up after the division in single precision as upstream divides. A quota past a signed 32-bit integer, which the kernel accepts, is no limit here, where upstream's `std::stoi` throws an exception its `catch (Error &)` does not catch and every command aborts. Otherwise it is the hardware thread count upstream's C++ runtime reports for `std::thread::hardware_concurrency`, at least 1, read through the same call, `sysconf(_SC_NPROCESSORS_ONLN)`: libc++ makes that call on macOS (16.0.6, which nixpkgs 24.05 builds upstream with), and on Linux libstdc++ calls glibc's `get_nprocs`, the function glibc's `sysconf` answers that name with (sysdeps/posix/sysconf.c at glibc 2.39). On Linux the glibc is the host's, where upstream's is nixpkgs' 2.39, and the two count the CPUs online alike on every glibc release but 2.34, whose `get_nprocs` counts the process's affinity mask. On Windows, where upstream has no local builder, the count is GHC's `getNumProcessors`. Upstream's `--cores` flag is not implemented.
- **Library API:** `Nix.Config.NixConfig` gains `ncCores :: Maybe Word32`, `Nothing` when no source sets it, and `Nix.Builder.BuildConfig` gains `bcCores :: Word32`, which `defaultBuildConfig` sets to 1, what setup.sh takes an unset `NIX_BUILD_CORES` to mean; a record built with the constructor needs the new field. The new module `Nix.Builder.Cores` gives upstream's default: `defaultCores` chooses it from a cgroup limit and a hardware count, `hardwareConcurrency` reads the hardware count, `cgroupCoreLimit` finds the limit over a file-reading effect (`ReadKernelFile`), and `cgroup2MountPoint`, `parseCgroups` and `cpuMaxCores` parse the three files it reads.
