- **A string value no longer takes a symbol, so the names an evaluation interns keep upstream's order however many strings it makes, and `builtins.seq "zb" (({ }: null) (builtins.listToAttrs [ { name = "za"; value = 1; } { name = "zb"; value = 2; } ]))` names `za` as the unexpected argument, as upstream does, where it named `zb`.** Upstream's symbol table holds names alone (`SymbolTable`, symbol-table.hh at 2.24.9): a string value points at bytes of its own (`Value::mkString`, eval.cc), and a set's attributes are sorted by the order their names were interned in, so that order decides which of two failures a walk over a set stops at first. nova-nix interned every string value in the same table, and so every string, URI, path and search-path literal, every source file's path and every store path and output name in a string's context, each moving the place of every name interned after it. A string's or a path's bytes now live in an arena of their own, made once where the string is made and shared by every cell that comes to hold it, as upstream copies a `Value` with the pointer to its bytes (value.hh at 2.24.9); the value of a string or URI literal, and of a path literal written in canonical form, is the literal's bytes in the compiled code, as upstream's `ExprString` hands out the value it holds (`ExprString::maybeThunk` in eval.cc). Equal strings made apart are two copies, where the symbol table kept one, as upstream's `makeImmutableString` copies the bytes of each string it makes (eval.cc); every empty string is one static, as upstream's is. A string holds at most 4 GiB of bytes, where upstream's has no bound of its own: its length is a `uint32_t`, the per-allocation limit across the C data layer, and a longer one fails evaluation with `CAllocationFailed` naming `nn_str_new`. The order in which a builtin makes the strings it returns no longer shows. The census `nova-nix eval` writes under `NOVA_NIX_C_STATS` counts strings as a kind of their own (`strings.*`), and its `symbols.*` lines count names alone: on `profiling/stress.nix` it counts 10,290 symbols where it counted 350,301, and 530,004 strings of 10.6 MB, and the bytes the allocators hold beyond their objects fall from 17.0 MB to 4.4 MB.
- **Library API:** `Nix.Eval.CStr` (new) binds the string arena: `cstrNew`, `cstrFromText`, `cstrBytes` and `cstrText` over a `CStrPtr`. `Nix.Eval.Symbol` no longer exports `symbolInternBytes` or `symbolBytes`. The string and path functions of `Nix.Eval.CThunk` (`cthunkNewComputedStr`, `cthunkNewComputedPath`, `cthunkSetComputedStr`, `cthunkSetComputedPath`) and the text, hash, name and output functions of `Nix.Eval.CCtxStr` take and answer a `CStrPtr` where they took a symbol's `Word32`. `Nix.Eval.CBytecode` exports `cbcEmitString`, `cbcEmitText`, `cbcString`, `cbcStringBytes` and `cbcStringText` for the compiled code's strings, and `Nix.Eval.CStats.PerKind` has a `kindStrings` field and `CRoot` the roots `RootString` and `RootCtxStr`. `NixValue`'s string and path constructors are `VStrHeld` and `VPathHeld`, which carry the `HeldBytes` their bytes already are in C; `VStr` and `VPath` are bidirectional pattern synonyms bundled with `NixValue`, which match one whatever it holds and build one held in Haskell only, so code that matches and builds strings and paths is unchanged. `Nix.Eval.Types` exports `heldString`, `stringCell`, `pathCell` and `StringCell`.
