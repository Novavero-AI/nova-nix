- **On macOS, `sandbox = true` runs a build under a profile of macOS's sandbox, as upstream's does: the build reads its inputs and the paths `sandbox-paths` names, writes only its outputs and its build directory, and reaches the network only when it is fixed-output.** `sandbox` stays off by default on macOS, as upstream's does (the `sandbox` setting in local-settings.hh at 2.36.0). The `nova-nix-sandbox` helper, now built and shipped for macOS too, applies the profile with `sandbox_init_with_parameters` in the builder's own process just before its exec, as upstream 2.36.0 applies its profile in the child it forks for the builder (`DarwinDerivationBuilder::setUser`), and passes upstream's parameters: `_NIX_BUILD_TOP`, the build directory; `_GLOBAL_TMP_DIR`, which is the build directory too (see below); and `_ALLOW_LOCAL_NETWORKING` for a derivation that sets `__darwinAllowLocalNetworking`. The profile is nova-nix's own text, written to the rules of upstream's `sandbox-defaults.sb` and `sandbox-network.sb`: everything is refused unless allowed; the build may write `/tmp` itself and its build directory, start processes and signal its own, read the system's version, time zones and locales, use POSIX semaphores and the standard devices, and it may make no file setuid or setgid; a fixed-output build also reaches the network, resolves names and checks certificates; any other reaches no network, or the loopback alone under `__darwinAllowLocalNetworking`. The build sees its build directory and its outputs where they are on disk, and is told upstream's `HOME`, `/homeless-shelter`. The profile names the store directory and the build directory as the kernel resolves them, since macOS's sandbox matches a file by its resolved path, so a store reached through a link, such as one beneath `/var`, still matches; upstream names its store and build directory as given. Each path is escaped in the profile's strings, as upstream escapes it (`sbplQuote`), and the store paths are grouped by the first character of their hash, each group under a guard of its own, as upstream groups them: macOS compiles the path filters of one operation into one table of at most 64 KiB, however many forms hold them, so a closure of some thousands of paths needs the groups. Where upstream lets a build write its inputs and the paths `sandbox-paths` names, under build users who own none of them, nova-nix's builder runs as the invoking user, who owns the store and any file a `sandbox-paths` entry may name, so the build may only read and run them, as the Linux sandbox binds every host path read-only. `sandbox-paths` defaults on macOS to upstream's `/System/Library/Frameworks`, `/System/Library/PrivateFrameworks`, `/bin/sh`, `/bin/bash` and `/usr/lib` (the macOS defaults in globals.cc), and an entry there must name one path on both sides of its `=`, as upstream's must. A derivation's `__impureHostDeps` may each name a path at or beneath an entry of the new `allowed-impure-host-deps`, whose macOS default is upstream's `/System/Library`, `/usr/lib`, `/dev` and `/bin/sh`, and its `__sandboxProfile` ends the profile under `relaxed`, where `sandbox = true` refuses it in upstream's words (`makeDerivationBuilder` in unix-derivation-builder.cc). A `__sandboxProfile` that is not a string, or an `__impureHostDeps` that is not a list of strings, in structured attributes is refused in upstream 2.36.0's words, its JSON type error after `while parsing derivation '...': while parsing attribute "...": `. The new `darwin-log-sandbox-violations` sends what a profile refuses to the system log. A path a build may not do without that is missing fails the build in upstream's words, `getting attributes of required path '`, whose quote upstream's format never closes. A profile macOS refuses fails the build as `while setting up the build environment: failed to configure sandbox`, with upstream's line and macOS's reason in the build log, where upstream reports the end of the builder's pipe while it waits for the build environment, that line among the messages before it. A `sandbox-paths` target that is not absolute is refused, where upstream loops forever. The builder leads a session of its own; an interrupt, the end of nova-nix, or the builder's own end kills every process left in its group before the builder is reaped, as upstream kills the group before it waits. The helper checks once per process that macOS takes a profile from it; where it does not, as for a process already in a sandbox, or where the helper is missing, a sandboxed build fails whatever `sandbox-fallback` says, as upstream reads `sandbox-fallback` on Linux alone (`makeDerivationBuilder`) and fails a macOS build whose sandbox cannot be made, in its words, `while setting up the build environment: failed to configure sandbox`. As root a sandboxed build is refused, as on Linux. Unsandboxed builds on macOS are unchanged: upstream holds them to a profile that refuses setuid and setgid files (`sandbox-minimal.sb`), and it picks a universal builder's architecture from the derivation's system (`DarwinDerivationBuilder::execBuilder`), neither of which nova-nix does yet.
- **A macOS build reaches none of the invoking user's own files, sockets, terminals or shared memory, and none of its processes outlives it, where upstream's profile assumes a build user of its own.** Upstream runs a macOS build as a build user, who owns nothing beyond the build, and its profile grants what is harmless for that user; nova-nix runs the builder as the invoking user, so the profile leaves out each grant that would reach that user's own resources, until builds run as build users of their own under a daemon. Upstream's `_GLOBAL_TMP_DIR` is the temporary directory Nix runs with, `TMPDIR` or `/tmp`, which the build may write and connect a Unix socket in; nova-nix's is the build's own directory, which the builder's `TMPDIR` names already, so a build reaches none of the user's live sockets and files in the temporary directory. Upstream's default `sandbox-paths` on macOS also name `/private/tmp` and `/private/var/tmp`; nova-nix's leave them out for the same reason. Upstream allows pseudo-terminals and the terminal devices; nova-nix refuses them and `/dev/console` after every other rule, so `/dev` among a derivation's `__impureHostDeps` reaches none either, since a build that opened one of the user's terminals would read what is typed there and write to it. A build that needs a pseudo-terminal of its own waits for build users. Upstream allows POSIX and System V shared memory and semaphores; nova-nix allows POSIX semaphores alone, which Python's `multiprocessing` takes, since the others would attach the user's own, a PostgreSQL server's System V segment among them. A build that uses System V IPC, PostgreSQL's own tests among them, fails until build users. Upstream ends a build by killing every process of its build user (`UnixDerivationBuilderImpl::killSandbox`, which calls `killUser` in processes.cc); nova-nix's helper, which cannot do that as the invoking user, ends every process that carries the build's mark: a Mach service name, random and made by the helper for that build alone, which the build's profile allows as its last rule, beside a second it refuses. Under `sandbox = true` no other process's sandbox answers the same and the build cannot change the answer; under `relaxed` a derivation's own profile can redefine the forms that state the mark, as `relaxed` already lets a derivation build with no sandbox at all. The helper asks a process about the refused name first, so one that applies a sandbox of its own between the two questions is not taken for the build's. Each time it lists the user's processes it stops every process of the build it finds, those it stopped before included, since one of them may continue another; once a listing finds none new, it kills them, waits for each to end, and lists again, and it reports the build as it ended only when a listing taken after that finds none of the build's left, nor any process that ended before it could be asked. Its listings are bounded, and a build whose processes are still found when they run out, or whose killed processes cannot be watched or do not end in time, fails. It does so after the builder ends and on every way the helper ends: the end of nova-nix, an interrupt, or any terminating signal it can catch, `SIGUSR1` among them. The builder writes its output to a pipe the helper copies into the build log, so the log, and nova-nix's wait for it, ends when the helper does, even when a process of a failed build still holds that pipe; and the helper never blocks on the log, so interrupting a build whose builder writes without pause ends it at once, while a slow or paused reader of the log, such as a pager, never fails a build. So a process of the build that leaves the builder's process group by a session of its own cannot outlive the build and change its output once it is registered, and nova-nix's helper is gone only once the build's processes are, unless it is killed with `SIGKILL`, which no process can catch. A signal the helper inherits ignored, as `SIGHUP` under `nohup`, does not end the build, since the helper runs in nova-nix's process group and upstream's builder, in a session of its own, never sees one sent there. Two exposures remain while the builder runs as the invoking user: a build may create System V shared memory segments and semaphores, which no profile rule refuses, though it can neither use nor remove one, so each outlives the build, counts against the system's limit (`kern.sysv.shmmni` segments) and may hold a key one of the user's programs wants; and a build may read the command lines of the user's other processes (`KERN_PROCARGS2`), which neither `sysctl-read` nor `process-info*` rules reach, where the kernel refuses a build user another user's. Both close once builds run as build users.
- **Library API:** `Nix.Builder.Sandbox` gains macOS's sandbox: `SandboxBackend`, `hostSandboxBackend` and `backendFallback`; the macOS defaults (`darwinSandboxPaths`, `darwinImpureHostPrefixes`); a derivation's `DarwinOptions` (`darwinOptions`); the paths a profile names (`darwinPathsInSandbox`, `darwinPathTarget`, `profileFilter`), the profile itself (`darwinProfile`), the helper's macOS plan (`DarwinPlan`, `darwinParameters`, `renderDarwinPlan`) and its macOS steps (`DarwinStage`, `darwinSetupFailureMessage`). `sandboxUse` takes the host's backend first, `helperOutcome` takes the backend's stage names and report of a failed step in place of a Linux plan, `unavailableMessage` takes the backend, and `SandboxConfig` has two new strict fields, `scAllowedImpureHostDeps` and `scViolationLog`. `Nix.Builder.Sandbox.Spawn`'s `sandboxAvailability` answers the backend with the helper, `sandboxSupported` is removed, and `profileFilters` and `resolvedPath` are added. `Nix.Config.NixConfig` has two new strict fields, `ncAllowedImpureHostDeps` and `ncDarwinLogSandboxViolations`. `Nix.Realise` exports `derivationStringAttr` and `derivationStringsAttr`, upstream's `getStringAttr` and `getStringSetAttr`. `Nix.Json` exports `expectJson`, upstream's `ensureType`, which `Nix.Daemon.Protocol` used privately.
