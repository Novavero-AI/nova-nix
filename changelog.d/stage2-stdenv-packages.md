- **`stage2Stdenv` bundles each DLL an output's programs and libraries import from a build input beside them, as the stage-1 stdenv does, and builds the stage-1 stdenv's six packages: GNU Hello, GNU sed, zlib as a DLL, libgreet, and zdemo and greeter, which link zlib and libgreet.** Windows has no RPATH, so a program finds a DLL in its own directory before the system's and PATH's, and a program that links a DLL from another package runs only with that DLL beside it. The stage-2 stdenv now runs its own setup script, which runs the seed stdenv's unchanged for every phase from unpack to install and then that fixup phase, reading each PE file's imports with binutils' `objdump` to a fixpoint and failing the build on a DLL that is neither a system one nor in a declared input; the seed ladder's rungs are untouched. `OBJDUMP` and `STRIP` name binutils' programs by their paths, as nixpkgs' bintools wrapper names them, since the stdenv keeps its toolchain off `PATH`, and `WINDRES` names a `windres` wrapper beside the compiler wrappers: windres preprocesses through `cmd.exe`, which cannot run the stdenv's `gcc`, a script, so the wrapper gives windres the native `gcc.exe` as its preprocessor, under the environment the `gcc` wrapper gives it. zlib's build passes `WINDRES` and `STRIP` to its makefile, which names them otherwise, and GNU sed's configure takes `WINDRES` from the environment for its tests' resource files.
