- **`pkgs/windows` builds GNU binutils 2.41 for `i686-w64-mingw32` with the seed stdenv, compiled by `tinycc-native`: the assembler, linker, archiver and object tools, running on i686 Windows and writing i686 PE and COFF.** It follows nixpkgs' `minimal-bootstrap/binutils`, which builds the same release with tinycc. The target is the triple MinGW-w64's own build guide configures binutils for and the one under which GCC 4.6.4 takes MinGW-w64's feature set, where any other vendor is mingw.org's; the stdenv's `i686-pc-mingw32` stays the build and the host, so the tools install as `bin/i686-w64-mingw32-<name>.exe` and again under their plain names in `i686-w64-mingw32/bin`. nixpkgs' later `fix-tinycc-attribute.patch` is applied unchanged: `include/ansidecl.h` defines `__attribute__` away for a compiler that is not GCC, and TinyCC's headers spell `__stdcall` as an attribute, so without it a source that reads `ansidecl.h` before `windows.h` calls every Windows API function as cdecl and pops arguments the function has already popped, in bfd on each file it opens. A second patch, of its own, opens in binary mode the temporary file that `ar` and `ranlib`, and `objcopy` and `strip` rewriting a file in place, write their output to and copy into place: without `mkstemp`, which msvcrt.dll lacks, `make_tempname` opens it with no `O_BINARY`, msvcrt treats it as text, and the copy ends at the first 0x1A byte, so an archive of libgcc's objects comes out cut short. MinGW-w64's runtime supplies a `mkstemp` that opens in binary, so its own builds of binutils never reach that open. nixpkgs' `deterministic.patch` is not applied, since the flag it sets is read by the archive and XCOFF writers and not by the PE writer, which stamps an image with the time unless ld is run with `--no-insert-timestamp`. The build leaves out what TinyCC's headers and msvcrt.dll cannot carry: the bundled libintl, whose declaration of `alloca` tcc rejects, plugin support, which reads a directory with `opendir`, and libctf, which includes `sys/param.h`. libbfd is installed, as in nixpkgs' native build, since libtool otherwise unpacks libsframe into libbfd member by member and `tcc -ar` keeps 15 characters of a member's name, which libsframe's three objects share. ld has no built-in search path, as in nixpkgs, and here also because its `genscripts.sh` splits the path at a drive letter's colon. Two compatibility headers add what MinGW-w64's headers have and TinyCC's lack: `alloca` as a macro, and `rpcdce.h` for the `UuidCreate` call behind `--build-id=uuid`. The seed stdenv gains what the build needs of it: a patch phase, nixpkgs' `patches`; `srcs` on what `mkDerivation` returns, as the stage-1 stdenv states it; and three `config.site` settings without which libtool takes tcc and its linker for Microsoft's, archives with `lib`, names a static library `.lib` and passes each source through `cygpath`. Since those settings have configure take tcc for GCC, which it gives `-g -O2` where CFLAGS is unset, `config.site` also gives CFLAGS an empty default that a package's own still overrides: tcc's debugging information names the directory tcc ran in and each file by the path it opened, a header from the store by the store's physical path, so a program built with it would differ with the store's drive and with the user whose temporary directory the build ran in, and tcc's `-O` only defines `__OPTIMIZE__`. make runs `$NIX_BUILD_CORES` jobs in one run, where nixpkgs' `minimal-bootstrap/binutils` builds ld on its own for a race between jobs over `ld/.deps/ldwrite.Po`, a file dependency tracking writes and `--disable-dependency-tracking` keeps the compile rule from writing. CI builds binutils on x64 and ARM64 Windows, checks `ld --version`, and has `as` assemble a function, `ar` archive it and `ld` link it into a program that runs and exits with the function's value, and has `ar` archive and extract a file holding a 0x1A byte and a CR LF unchanged.
